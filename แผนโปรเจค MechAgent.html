ปัญหาและผู้ใช้

ร่างแรกสำหรับทีม ปรับถ้อยคำและตัวเลขได้ ตัวเลขที่เป็นสมมติฐานติดป้ายไว้

Problem statement

ลูกปืนเป็นสาเหตุอันดับต้นของมอเตอร์และปั๊มเสีย งานสำรวจที่อ้างอิงกันบ่อย (IEEE / EPRI) พบว่าราว 40% ของมอเตอร์ที่เสียเกิดจากลูกปืน

โรงงานขนาดกลางส่วนใหญ่ยังตรวจลูกปืนด้วยการเดินฟังเสียงหรือวัดการสั่นเดือนละครั้ง ความเสียหายที่เริ่มระหว่างรอบตรวจจึงมักถูกพบเมื่อเครื่องหยุดกะทันหันแล้ว เมื่อพบปัญหา หัวหน้ายังต้องเช็คเครื่องสำรอง อะไหล่ ตารางผลิต และหาคู่มือเองก่อนสั่งงาน ซึ่งใช้เวลาหลายชั่วโมง

MechAgent ตรวจการสั่นตลอดเวลา บอกว่าเสียตรงไหนและเหลือเวลาเท่าไหร่ แล้วให้ Agent เตรียมรายงานและใบสั่งงานพร้อมขั้นตอนให้ช่าง ภายในไม่กี่นาที โดยคนเป็นผู้อนุมัติทุกครั้ง

User persona

หัวหน้ากะซ่อมบำรุงผู้อนุมัติปัญหา: ต้องรวบรวมข้อมูลจากหลายระบบก่อนตัดสินใจ รู้ตัวช้าเมื่อเครื่องเริ่มเสียได้อะไร: รายงานพร้อมหลักฐานใน Telegram กดอนุมัติได้ทันที
ช่างซ่อมบำรุงผู้ลงมือปัญหา: ได้รับงานแบบไม่มีรายละเอียด ต้องเดาว่าต้องเตรียมอะไรได้อะไร: ขั้นตอนตรวจ แก้ไขเบื้องต้น อะไหล่ และข้อควรระวังด้านความปลอดภัย
ผู้จัดการโรงงานผู้รับเรื่องที่ถูกส่งต่อปัญหา: เครื่องหยุดกะทันหันกระทบแผนผลิตและค่าใช้จ่ายได้อะไร: ได้รับแจ้งอัตโนมัติเมื่อเรื่องวิกฤตไม่มีคนรับ และเห็นตัวเลขคุณค่าที่ระบบสร้าง

Workflow แบบง่าย

เซนเซอร์สั่น → AI ตรวจ (เสียตรงไหน + เหลือเท่าไหร่) → Agent เตรียมรายงาน → หัวหน้าอนุมัติใน Telegram → ช่างได้ขั้นตอน → บันทึก audit log

ภาพรวม: ข้อมูลไหลผ่าน 9 ขั้น

ขั้น 1–6 ทำงานตลอดเวลาด้วยตัวเลขและสูตร ไม่ใช้ LLM ส่วน LLM ถูกปลุกที่ขั้น 7 เท่านั้น เมื่อ Gatekeeper ยืนยันว่ามีปัญหาจริง

ลูกปืนมี 4 ชิ้นส่วน จึงมี 5 คลาส

แต่ละชิ้นเมื่อเสียจะ "ก๊อก" ด้วยจังหวะเฉพาะตัว วัดเป็นจำนวนครั้งต่อการหมุนเพลา 1 รอบ (Order) ตัวเลขด้านล่างเป็นของลูกปืนรุ่น SKF 6205

ปกติไม่มียอดความเสียหาย มีแค่การสั่นของเครื่องจักรทั่วไป
รางใน≈ 5.42 เท่าของรอบเพลาวงในที่หมุนไปกับเพลา
รางนอก≈ 3.58 เท่าของรอบเพลาวงนอกที่อยู่กับที่ในตัวเรือน
ลูกบอล≈ 2.36 เท่าของรอบเพลาลูกกลิ้งระหว่างรางทั้งสอง
กรง≈ 0.40 เท่าของรอบเพลาตัวยึดระยะห่างของลูกบอล ตรวจยากที่สุดและถือว่าวิกฤตเสมอ

ทำไมใช้ข้อมูลจำลอง

เวลาของ Hackathon จำกัด การดาวน์โหลดและทำความสะอาด dataset จริงหลายชุดใช้เวลามาก ตัวจำลองตามหลักฟิสิกส์ให้ข้อมูลครบทุกอย่างที่โปรเจคต้องการ

สิ่งที่ต้องการdataset จริงที่หาได้ตัวจำลอง
ครบ 5 คลาส (รวมกรง)มีน้อยชุด และ label ของกรงมักปนกับรางนอกครบ
ลูกปืนที่ค่อยๆ เสียจนพัง พร้อมเวลาต้องใช้อีกชุดแยก และมีไม่กี่ลูกสร้างได้หลายสิบลูก
หลายความเร็วรอบ หลายรุ่นลูกปืนแต่ละชุดมีไม่กี่แบบกำหนดได้เอง
label ถูกต้องบางไฟล์ label ไม่ตรงกับสัญญาณถูก 100%

รับมือคำถาม "สร้างเอง ทดสอบเอง ก็ต้องแม่นอยู่แล้วสิ"

วิธีตอบกรรมการว่า
จำลองตามฟิสิกส์สร้างตามแบบจำลองมาตรฐานทางวิชาการ (McFadden & Smith, Randall & Antoni) ไม่ได้สุ่มตัวเลขมั่ว
สุ่มทุกค่า + ใส่ตัวหลอกไม่มีสองตัวอย่างที่เหมือนกัน และมีเครื่องที่สั่นเหมือนเสียแต่ลูกปืนไม่เสีย
ข้อสอบไม่เหมือนตอนสอนทดสอบกับความเร็ว รุ่นลูกปืน และ noise ที่ AI ไม่เคยเห็น
โชว์จุดที่ระบบพลาดกราฟความแม่นเมื่อ noise หนักขึ้น แสดงว่าทีมรู้ขีดจำกัดของระบบ
เทียบกับข้อมูลจริงวาดสัญญาณจำลองเทียบกับ CWRU จริง หน้าตาเหมือนกัน (ไม่บังคับ)
บอกกรรมการตรงๆ ว่าใช้ข้อมูลจำลอง: "ข้อมูลจำลองสร้างตามสูตรฟิสิกส์ของลูกปืน ทดสอบกับความเร็ว รุ่นลูกปืน และระดับ noise ที่โมเดลไม่เคยเห็น มีตัวหลอก และแสดงว่าระบบเริ่มพลาดที่ noise ระดับไหน"

ทีละขั้น: ทำอะไร และรับมือปัญหาอะไร

1

ตัวจำลองสัญญาณลูกปืน

หัวใจของโปรเจค ใช้แทน dataset จริงทั้งหมด

ข้อมูลที่สร้างใช้ทำอะไร
สัญญาณสั้น 1 วินาที ของแต่ละคลาส (หลายพันชิ้น)สอน AI ว่าเสียตรงไหน
ลูกปืนที่ค่อยๆ เสียจนพัง พร้อมเวลากำกับ (หลายสิบลูก)สอนและทดสอบการทำนายอายุ
ความสมจริง 7 อย่าง
  1. ลูกบอลกลิ้งผ่านรอยแตกแล้ว "ก๊อก" เป็นจังหวะ
  2. ตัวเครื่องก้องหลังก๊อกแต่ละครั้ง เหมือนเคาะระฆัง
  3. จังหวะก๊อกคลาด 1–2% เพราะลูกบอลลื่นไถล
  4. แรงก๊อกดังบ้างเบาบ้าง ตามตำแหน่งที่รับน้ำหนัก
  5. เสียงเครื่องจักรปกติ (เพลาหมุน ไฟฟ้า 50 Hz)
  6. noise และแรงกระแทกสุ่ม
  7. ความเสียหายโตแบบไม่เรียบ บางช่วงดูเหมือนดีขึ้นชั่วคราว
รับมืออะไร
  • AI จำข้อสอบ → สุ่มความแรงของความเสียหาย ความถี่ก้อง ขนาดสัญญาณ และ noise ทุกชิ้น
  • แจ้งเตือนผิด → มีตัวหลอก (เพลาไม่สมดุล ไม่ตรงแนว ไฟฟ้ารบกวน) ที่ต้องตอบว่า "ปกติ"
  • ใช้ได้แค่เครื่องเดียว → ลูกปืน 3–4 รุ่น เก็บไว้ 1 รุ่นเป็นข้อสอบ
  • ความเร็ว → สอนที่ 1,800 รอบ/นาที (แกว่ง ±2% เหมือนมอเตอร์จริง) แล้วสอบที่ความเร็วอื่น
2

เตรียมสัญญาณ

เปลี่ยนตัวเลขดิบหลายหมื่นตัวให้เป็น 512 ตัวเลขที่ AI อ่านง่าย

ตัวเลขดิบ → ตัดเป็นท่อน → กรองเอาเฉพาะเสียงก๊อก (1–5 kHz) → หาจังหวะก๊อก (envelope) → หารด้วยความเร็ว (Order) → ปรับให้ลูกปืนทุกรุ่นเทียบกันได้ → 512 ตัวเลข → AI
รับมืออะไร
  • ความเร็วต่างกัน → หารด้วยความเร็ว ลายเซ็นอยู่ตำแหน่งเดิม (ดู แกน Order)
  • ลูกปืนต่างรุ่น → ปรับแกนให้ความถี่ความเสียหายของทุกรุ่นตรงกัน
  • เสียงเครื่องจักรอื่นกลบ → กรองเอาเฉพาะช่วงความถี่ที่เสียงก๊อกปรากฏ
3

AI ทายว่าเสียตรงไหน

  • โมเดล: 1D-CNN ขนาดเล็ก (ประมาณ 27,000 พารามิเตอร์) รันบน CPU ได้
  • 5 ตัวช่วยกันโหวต (ensemble): ผลนิ่งกว่า ความมั่นใจเชื่อได้มากกว่าตัวเดียว
  • ตอนสอนเพิ่มความยาก: สุ่ม noise ไฟฟ้ารบกวน ยืด/หดสัญญาณ
  • ผลลัพธ์: ชนิดความเสียหาย + ความมั่นใจ เช่น รางนอก 94%
4

ฟิสิกส์ตรวจซ้ำ

คำนวณตามสูตรว่าลูกปืนรุ่นนี้ที่ความเร็วนี้ ถ้าเสียแต่ละแบบต้องสั่นที่ความถี่ไหน แล้วดูว่ามียอดตรงนั้นจริงไหม

ผลตรวจระบบทำอะไร
AI กับฟิสิกส์ตรงกันมั่นใจขึ้น
AI บอกปกติ แต่ฟิสิกส์เห็นยอดชัดมากเชื่อฟิสิกส์ กันพลาดเคสอันตราย
หลักฐานอ่อนใช้คำว่า "สงสัย" สั่งตรวจก่อน ไม่สั่งเปลี่ยนทันที

ผลนี้ใช้เป็นเหตุผลในรายงาน เช่น "พบยอดที่ 3.58 เท่าของรอบเพลา ตรงกับรางนอก"

5

ทำนายอายุที่เหลือ (RUL)

ไม่ใช่โมเดล AI ที่ต้องเทรน เป็นการต่อเส้นแนวโน้ม เหมือนดูเกจน้ำมันลดลงแล้วเดาว่าจะหมดเมื่อไหร่

  1. วัดความแรงของการสั่นทุกครั้ง (Health Indicator)
  2. ถือว่าเริ่มเสียเมื่อแรงกว่าปกติต่อเนื่อง 5 ครั้ง
  3. ต่อเส้นแนวโน้มที่โตเร็วขึ้นเรื่อยๆ (exponential)
  4. ดูว่าเส้นชนจุดพังเมื่อไหร่ → เหลือกี่ชั่วโมง/วัน
  5. บอกช่วงความไม่แน่นอน เช่น "3–5 วัน"
รับมืออะไร
  • วัดห่างไม่เท่ากัน → ใช้เวลาจริงจาก timestamp ไม่ใช่ลำดับไฟล์

  • เพิ่งเริ่มเสีย → ยังบอกเวลาไม่ได้ ระบบตอบ "เริ่มเสื่อม เฝ้าระวัง" แทนการเดา

Agent เขียนรายงาน ใช้ LLM

Agent ไม่ได้เดินตามสคริปต์ มันเลือกเองว่าจะเรียกเครื่องมือไหนต่อ ตามข้อมูลที่ได้ในแต่ละรอบ

วิธีทำงาน: วางแผน → ลงมือ → สรุป
1. รับเหตุการณ์จาก Gatekeeper 2. เขียนแผนงาน "ต้องรู้: เครื่องสำรอง · อะไหล่ · ช่วงหยุดได้ · วิธีแก้" 3. เรียกเครื่องมือทีละตัว อ่านผล แล้วตัดสินใจขั้นถัดไป (ปรับแผนได้) 4. ค้นคู่มือ (RAG) ตามชนิดความเสียหาย 5. ส่งรายงาน → ระบบตรวจรูปแบบ → ส่งให้หัวหน้าอนุมัติ

ทุกขั้นถูกบันทึกเป็น trace (แผน · เครื่องมือที่เรียก · ข้อมูลที่ส่ง · ผลที่ได้ · ข้อความจากคู่มือที่ค้นเจอ) แล้วแสดงในแท็บ "Agent คิดอะไร" บน Dashboard ให้กรรมการเห็นว่า Agent คิดเองจริง

รับมืออะไร
  • LLM ตอบผิดรูปแบบ → ระบบตรวจแล้วให้แก้ ถ้ายังผิดใช้ตัวเขียนสำรองแทน demo จึงไม่พังกลางคัน
  • LLM วนไม่จบ → จำกัดไม่เกิน 10 รอบ
  • หลักฐานอ่อน → รายงานใช้คำว่า "สงสัย" และไม่สั่งซื้ออะไหล่
  • Agent ทำเกินหน้าที่ → guardrails: เครื่องมือของ Agent ทำได้แค่อ่านข้อมูลและ ร่าง เอกสาร ไม่มีเครื่องมือหยุดเครื่องหรือส่งคำสั่งซื้อจริง (ดู ความปลอดภัยของ AI)
RAG และ custom chunking

คู่มือถูกตัดเป็นชิ้นตาม หัวข้อ ไม่ใช่ตัดตามจำนวนตัวอักษร ทุกชนิดความเสียหายมีหัวข้อเดียวกัน ทำให้ค้นเจอส่วนที่ต้องใช้ตรงจุด

B

รับปุ่มอนุมัติ Telegram แบบ webhook

ในเครื่อง โปรแกรมคอยถาม Telegram ตลอดว่ามีใครกดปุ่มหรือยัง (long polling) ซึ่งต้องเปิดโปรแกรมทิ้งไว้ บน AWS แบบนั้นเสียเงินทุกชั่วโมงและขัดกติกา

ในเครื่องบน AWS
วิธีรับปุ่มคอยถาม Telegram ตลอดTelegram ส่งมาบอกเองตอนมีคนกด
ต้องเปิดเครื่องทิ้งไว้ใช่ (ไม่มีปัญหาในเครื่องตัวเอง)ไม่ ทำงานเฉพาะตอนมีคนกด

เหมือนเปลี่ยนจากเดินไปเช็คตู้จดหมายทุก 5 นาที เป็นให้บุรุษไปรษณีย์กดกริ่งตอนจดหมายมา

โครงบน AWS (ร่าง)

ข้อมูลเซนเซอร์ (จำลอง) → S3 ↓ Lambda: เตรียมสัญญาณ + CNN + ทำนายอายุ + Gatekeeper ↓ เจอปัญหา Lambda: Agent → Bedrock (Claude หรือ Nova) + ค้นคู่มือ ↓ DynamoDB: เก็บเหตุการณ์ / รายงาน / สถานะการอนุมัติ ↓ Telegram ⇄ API Gateway + Lambda (รับปุ่มอนุมัติแบบ webhook) EventBridge Scheduler: ทุก 5 นาที เช็คว่าใครไม่กด → ส่งต่อผู้จัดการ

ทุกตัวเป็น serverless คิดเงินตามการใช้จริง ไม่มีเครื่องเปิดทิ้งไว้ ส่วน Dashboard รันในเครื่องตอนโชว์ เพราะ Streamlit บน cloud ต้องเปิดเครื่องตลอด

แสดงความประหยัดให้กรรมการเห็น

  • Gatekeeper กรองให้ LLM ทำงานเฉพาะตอนมีปัญหา โชว์ตัวเลข "วัด X ครั้ง ปลุก Agent Y ครั้ง"

  • Serverless ทั้งหมด ไม่มีเครื่องเปิดทิ้งไว้ ไม่ใช้งานก็แทบไม่เสียเงิน
  • ภาพหน้าจอ AWS Cost Explorer และลิงก์ Pricing Calculator ใส่ในสไลด์นำเสนอ

1D-CNN
โมเดล AI ที่อ่านข้อมูลเป็นแถวตัวเลข หารูปแบบยอดแหลมในสเปกตรัม
Envelope
การดึง "จังหวะก๊อก" ออกจากเสียงก้องของตัวเครื่อง ทำให้เห็นความถี่ความเสียหายชัดขึ้น
Order
จำนวนครั้งที่สั่นต่อการหมุนเพลา 1 รอบ (Hz ÷ ความเร็วเพลา)
Health Indicator
ตัวเลขเดียวที่บอกความแรงของการสั่น ใช้ดูแนวโน้มว่าลูกปืนแย่ลงเร็วแค่ไหน
RUL
Remaining Useful Life อายุที่เหลือก่อนพัง
Ensemble
สอนโมเดลหลายตัวแล้วให้โหวตรวมกัน
Gatekeeper
ด่านกฎที่ตัดสินว่าจะปลุก Agent หรือไม่
Agent
LLM ที่เลือกเรียกเครื่องมือเองทีละขั้นจนได้คำตอบ
RAG
ให้ LLM ค้นคู่มือก่อนตอบ แทนการตอบจากความจำ
LOTO
Lockout/Tagout ตัดพลังงาน ล็อก และติดป้าย ก่อนทำงานกับเครื่อง
Ollama
โปรแกรมฟรีสำหรับรัน LLM ในเครื่องตัวเอง
Trace
บันทึกทุกขั้นที่ Agent คิดและทำ ใช้แสดงให้เห็นว่า Agent ตัดสินใจยังไง
Guardrails
ขอบเขตที่ห้าม AI ทำ เช่น ห้ามสั่งหยุดเครื่องเอง
Audit log
ประวัติการกระทำทั้งหมดพร้อมเวลา ตรวจย้อนหลังได้
Webhook
ให้ระบบอื่น (เช่น Telegram) ส่งข้อมูลมาหาเราเองเมื่อมีเหตุการณ์
